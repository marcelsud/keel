Install Keel and start a service

On Linux amd64/arm64, Apple Silicon macOS, or Windows with WSL, install the CLI from its GitHub release:

Install the CLI
curl -fsSL https://github.com/marcelsud/keel/releases/latest/download/install.sh | sh

The installer adds keel to your PATH when needed. Open a new terminal, then check the version:

Check the installed CLI · v0.2.1 or later
keel --version

The release includes the contract generators. The TypeScript starter uses the published SDK 0.2.1. See the CLI reference for upgrade options.

With Bun 1.3+ installed, create an empty project directory, then initialize and start your application:

Terminal 1 · create your service
mkdir greeter
cd greeter
keel init

In a terminal, keel init asks for the project directory, language, and starter. Press Enter at each prompt to use the current directory, TypeScript, and the JSON greeting example:

Setup choices · press Enter to accept each default
Project directory (current directory or a new path) [.]:
Language (typescript/go) [typescript]:
Starter (empty/json/protobuf) [json]:

The setup installs the SDK and creates your service, client, and configuration. Start them with:

Terminal 1 · start your service
keel dev

This tutorial uses the TypeScript JSON example. You can also choose Go, a Protobuf example with generated contracts, or an empty service without sample actions or a client. See the CLI reference for scripted setup. Use the language selector for the SDK component examples below.

Wait for greeter ready. In a second terminal, from the same project directory:

Terminal 2 · call your service
bun run src/client.ts
Expected output
Hello, Ada!

Edit the greeting in your service and save. Keel restarts it; call the client again to see the change. Ctrl-C stops the service and local environment. init preserves existing projects by requiring a new or empty directory.

src/service.ts registers and runs your service; src/client.ts sends a request and exits. keel dev starts src/service.ts. Run bun run check to type-check both files.

New projects use keel.toml. Existing keel.json files remain supported; keep only one configuration file per project.

Run one keel dev per project. Use the second terminal for the client command above. Another environment cannot use the same data directory while the first is running.

See the generated service, client, and startup configuration
src/service.ts · register and serve the greet action
import { createKeel } from "@marcelsud/keel.ts";

const app = await createKeel({
  name: "greeter",
  url: process.env.KEEL_URL,
  token: process.env.KEEL_TOKEN,
});

app.action({
  name: "greet",
  args: app.schema.object({ name: app.schema.string() }),
  handler(_ctx, input) {
    return { message: "Hello, " + input.name + "!" };
  },
});

await app.start();
console.log("greeter ready");
console.log("Try: bun run src/client.ts");
src/client.ts · send one request and close the connection
import { createKeel } from "@marcelsud/keel.ts";

const app = await createKeel({
  name: "greeter-client",
  url: process.env.KEEL_URL,
  token: process.env.KEEL_TOKEN,
});

try {
  const result = await app.call<{ message: string }>(
    "greeter", "greet", { name: "Ada" },
  );
  console.log(result.message);
} finally {
  await app.stop();
}
keel.toml · keel dev runs this command for you
command = ["bun", "run", "src/service.ts"]

[[targets]]
language = "typescript"
out = "src/generated"

The action's schema validates requests and infers input.name. The client result annotation describes the expected response; it does not validate that response at runtime.

Add contracts under proto/ when you need shared, versioned API types. keel dev then generates bindings automatically under src/generated/. JSON actions validate their input; generated protobuf contracts provide shared client and handler types across languages.

The component snippets below extend a connected application. Add their registrations before app.start() / app.Start(ctx). TypeScript component examples use Node.js 22+ or Bun; protobuf generation also needs Node.js 22+.

CLI v0.2.2+ includes embedded SQL with app.sql / ctx.sql in TypeScript and app.SQL / ctx.SQL in Go. Follow the native SQL setup for migrations and service credentials, or try the three-member cluster on Linux/WSL2. SQL callback transactions cover one service's database; other SDK writes still commit independently.

Startup troubleshooting

Message or symptomNext step
no protobuf contracts; skipping generationExpected for the starter. Keep the process running and wait for greeter ready. You can add protobuf later.
local environment is already runningKeep the first keel dev running. Run bun run src/client.ts in the second terminal. Stop the first process with Ctrl-C before starting it again.
Error listening on portAnother environment or application owns that port. Stop it, or use a different port for a separate project as shown below. A different port does not let two environments share one project's data directory.
unknown command "init"Rerun the CLI installer, then check keel --version. Use v0.2.1 or later.
app.schema is missingUpgrade the project's SDK with bun add @marcelsud/keel.ts@0.2.1, then run bun run check. Updating the CLI alone does not change an existing project's dependencies.
set command in keel.toml or keel.jsonkeel init creates the command for new projects. For an existing TypeScript project, set command = ["bun", "run", "src/service.ts"] in keel.toml.
both keel.toml and keel.jsonChoose one configuration file and remove the other. Keel reports an ambiguity error when both exist.
Use a different port or share an environment with another project

For a separate project with its own environment, start on a different port:

Terminal 1 · separate project, separate environment
keel dev --port 4223

Set the same URL when calling it from the second terminal:

Terminal 2 · client on port 4223
KEEL_URL=nats://127.0.0.1:4223 bun run src/client.ts

keel dev --port -1 chooses a free port. Copy the URL from keel ready into the client's KEEL_URL.

To share an already running environment instead, run this from another service project:

Another project · reuse the environment on port 4222
KEEL_URL=nats://127.0.0.1:4222 keel dev

KEEL_URL makes Keel connect your service to that environment. Each service still has its own name and startup command.

Handler context and errors

Action, subscription, and worker handlers receive the SDK building blocks. HTTP handlers receive the request, parameters, query, and body; call an action to reuse service logic.

Inside a handler

ctx.kv, ctx.collection, ctx.pubsub, ctx.queue, ctx.client(), ctx.call(), and ctx.log are available.

ctx.KV, ctx.Collection, ctx.Pubsub, ctx.Queue, ctx.Call(), and ctx.Log are available. Generated typed clients also accept the handler context.

Service errors

Throw ValidationError for a 400 response or ServiceError(code, message) for an explicit service error. Clients receive a ServiceError. Unexpected handler errors return 500.

Return &sdk.Error{Code: 400, Message: "..."} for an explicit service error. Callers can inspect it with errors.As. Unexpected handler errors return 500.

Requests and shutdown

Requests default to a 5-second timeout, configurable with timeout. Await app.stop() to drain active handlers and deliveries.

Pass a context.Context to calls. Requests use a 5-second timeout if the context has no deadline. app.Stop() drains active handlers and deliveries.

What is available today

Typed unary RPC, data operations, events, workers, and version coexistence are implemented. GitHub contract installation, dated EOL notices, and the alpha / beta / stable lifecycle are planned.
